# /ui：UI 设计改进总入口

`/ui-*` 都是 `impeccable` 命令的中文快捷入口，规则全部来自 impeccable，这里只负责菜单和选命令。

## 菜单（按顺序）

| 阶段 | 命令 | 做什么 | 什么时候用 |
| --- | --- | --- | --- |
| 0 准备 | `/ui-0-init` | 写产品档案 PRODUCT.md | 新项目第一步；已有就跳过 |
| 0 准备 | `/ui-0-document` | 从代码生成设计规范 DESIGN.md | 接手老项目；大改版后更新 |
| 1 体检 | `/ui-1-critique` | 体验评审打分，列优先问题 | 不知道哪里不好 |
| 1 体检 | `/ui-1-audit` | 技术体检：无障碍、性能、响应式 | 查技术质量 |
| 2 规划 | `/ui-2-shape` | 动手前规划流程和界面 | 改流程、做新页面 |
| 3 修改 | `/ui-3-adapt` | 手机和多尺寸适配 | 手机上不好用 |
| 3 修改 | `/ui-3-clarify` | 改文案、标签、报错 | 文字看不懂 |
| 3 修改 | `/ui-3-harden` | 报错、断网、溢出、多语言 | 准备上线、边界情况 |
| 3 修改 | `/ui-3-onboard` | 首次使用、空状态、引导 | 新用户不知道怎么开始 |
| 3 修改 | `/ui-3-layout` | 间距、对齐、层级 | 看着乱或挤 |
| 3 修改 | `/ui-3-distill` | 删掉多余元素和步骤 | 太复杂 |
| 3 修改 | `/ui-3-typeset` | 字体、字号、可读性 | 文字别扭 |
| 3 修改 | `/ui-3-optimize` | 加载、渲染、卡顿 | 卡、慢 |
| 4 收尾 | `/ui-4-polish` | 上线前打磨，关掉评审问题 | 上线前 |
| 5 沉淀 | `/ui-5-extract` | 重复样式收成组件和 token | 样式越改越乱 |

**更多（不常用，直接敲 `/impeccable <命令>`）**：`bolder` 更醒目、`quieter` 收敛太花的、`colorize` 加颜色、`animate` 加动效、`delight` 加点趣味、`overdrive` 炫技、`live` 在浏览器里点选元素出变体、`generate` 给指定元素出几个变体。

**常用路线**

- 新项目：`/ui-0-init` → 直接说"设计首页/某个页面" → `/ui-1-critique` → 3 修改 → `/ui-4-polish` → `/ui-0-document`
- 老项目改造：`/ui-0-document`（没有 PRODUCT.md 再加 `/ui-0-init`）→ `/ui-1-critique` → `/ui-2-shape`（要改流程时）→ 3 修改 → `/ui-4-polish`
- 只修一个问题：直接 `/ui 用中文描述问题`

## 怎么执行

**没有参数**：先原样输出上面的菜单表，再调用 `impeccable` skill，不带参数，让它按项目现状推荐 2–3 个下一步。转述推荐时，有对应 `/ui-*` 的就写 `/ui-*` 名字。不自动执行任何命令。

**有参数**（用户描述了问题）：按菜单"什么时候用"一列选最贴切的一个命令，用一句话说明选了哪个、为什么，然后调用 `impeccable` skill，`args: <命令> <用户描述里的目标>`，并完全按它的指令执行。两个命令都贴切时问用户一次；描述是"新做一个页面/改版"这类整体设计请求时，把原话交给 `impeccable` 自己分流。
