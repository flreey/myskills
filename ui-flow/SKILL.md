# /ui-flow → /impeccable shape（只定交互）

1. 调用 `impeccable` skill（Claude Code：Skill 工具，`skill: impeccable`；其他宿主加载同名 skill 并运行它的 `shape` 命令），`args` 写成：

   `shape <目标>：只定交互和状态。视觉方向不在本轮决定（之后由 /ui-style 从候选里锁定），跳过 Phase 2 的视觉世界和概念选择，不运行 concept-seed。`

   `<目标>` 是本次参数；没有参数时，用 PRODUCT.md 的首批页面（工具页或 app 主界面在前）。
2. 按 impeccable 的提问和确认节奏执行。PRODUCT.md 已写的事实不再问。
3. 简报先写主路径，再写各页面。主路径把页面串起来：
   - 至少三条：新用户从入口到第一次拿到价值，再到第一次付费；回头用户的日常循环；从外面进来的入口（邮件、通知、分享链接、API/MCP、首页再次输入）各自落到哪一页、看到什么状态。
   - 每一步写：在哪一页、看到什么或做什么、什么条件下进入下一步、发什么事件；最后列出每条路线会在哪几步离开。
   - 已有站点要对着代码走一遍：每一步的"下一步"在当前代码里真的会出现吗？出现不了的就是断点（比如免费用户做完该做的，下一步却还是原地），在简报里标"待实现"。
4. 各页面写清：
   - 谁、在什么情况下来，要完成什么；
   - 操作步骤；
   - 会改变画面的状态：首次进入（工具页先给一个现成示例，不放空表单）、输入中、加载、报错、空或超限输入、成功和下一步、额度或付费墙；
   - 手机上的不同之处；
   - 每个状态发哪个事件、带哪些字段（命名和字段按 site-measure 的 `references/tracking-plans.md`；北极星、开始、完成、报错、拿走结果这几个状态必须有事件；站点原有事件名不改，只写清它对应哪个标准事件）。事件跟着功能一起写，不留到上线前补。
5. 写事件时分清哪些事情不经过浏览器：后台任务（cron、队列，用户关了页面也会跑完）、API/MCP/令牌调用、webhook 等。浏览器事件只在页面打开时才发，这些情况会漏记甚至记不到。北极星、完成这类要拿来计数的指标，如果有一部分发生在浏览器之外，就以服务器或数据库的记录为准（写清来自哪张表、哪个字段，缺字段的标"待实现"），浏览器事件只用来看界面上的转化。
6. 站长确认后，把简报写进项目根目录的 `docs/flow.md`（已有就按路线和页面更新，不覆盖其他部分）。不写代码。

结束时一句话提示下一步：site-kit 新站先用 kit 默认样式把这些状态做出来点一遍，再进入第 3 阶段 `ui-style`；已有站点直接按 flow.md 实现，做完用 `/ui-critique`。
